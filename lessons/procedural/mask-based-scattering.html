Mask-based scattering on terrain

What this lesson explains: how this project plants firs and fly agarics. You do not place each model by hand. You throw many candidate points at the ground, keep only those the mask allows, sit them on the FBM hills, and draw the survivors as instances.

Goal

After this lesson you should be able to:

  • define a mask and say what it is used for;
  • define texture-based procedural scattering in one paragraph;
  • sketch this project's component tree and name the props each parent sends down;
  • explain rejection sampling with a density mask;
  • map a world position on the terrain to a UV and read a mask pixel;
  • seed a random number generator so a forest can change on reload or stay fixed for debugging;
  • place objects on a displaced plane after the -Math.PI / 2 X rotation;
  • instance a multi-mesh GLB instead of mounting one React tree per object.

What is a mask, and what is it used for?

A mask is a 2D image that does not shade the scene. It answers where and how much. Each pixel is a weight, usually from black (0) to white (1). Gray is a value in between.

Think of a stencil or a cookie cutter laid over the terrain. The picture is not the fir or the mushroom. It is a permission map: “this patch is allowed / this patch is forbidden / this patch is only half-allowed.”

Graphics uses masks for many jobs:

  • Visibility / cutout — hide parts of a mesh (leaves, a hole in a fence).
  • Selection — limit a paint stroke, a blur, or a color grade to a region.
  • Blend — mix two materials (dirt vs moss) by a painted weight.
  • Density / scatter — this lesson. The mask is a probability field. White means “a candidate here almost always lives.” Black means “always skip.” Gray means “maybe.”

In this project the mask is not stamped onto the ground as a texture you see. The soil still uses the pine-root PBR maps. The scatter maps stay off-screen. Code reads them: world point → UV → one pixel → a 0–1 density → keep or reject that candidate.

Two masks run at once because trees and mushrooms should not share the same living area:

  • scatter-maps/firs-scatter-map.png — white X. Firs cluster on the X.
  • scatter-maps/mushrooms-scatter-map.png — seven soft dots. Fly agarics cluster on the dots.

Terrain owns those two PNGs. It loads them with useTexture and never applies them to the ground material. A 1×1 white image is a mask too: density is 1 everywhere, so every candidate survives. That is how you test placement before you paint art.

What is texture-based procedural scattering?

Texture-based procedural scattering is a way to populate a surface with many objects without placing them by hand and without baking their positions into the scene. A program proposes candidate points. A texture — a painted black-and-white (or grayscale) map — decides how likely each point is to live. The code then writes a transform (position, yaw, scale) for every survivor and draws those copies cheaply.

Three ideas sit in that name:

  • Procedural — positions come from an algorithm (random candidates + rules), not from dragging 80 firs in a DCC app.
  • Texture-based — art direction is a 2D image aligned to the terrain UVs. White means “this patch wants life,” black means “keep this clear,” gray means “maybe.” You change the forest by painting, not by rewriting loops.
  • Scattering — many similar objects (trees, mushrooms) are distributed across a surface. The mask is not a stencil that stamps models onto pixels; it is a probability field the scatter loop samples.

That is different from:

  • hand-placed props (one transform per object, authored once);
  • noise-only scatter (no painted shape — only math, so you cannot draw an X or seven rings);
  • a particle system (good for thousands of dots of light, not for a GLB with materials).

In this project the texture is the density mask. The procedure is: random point on the plane → UV → read the mask → keep or reject → sit on the FBM height → instance the GLB. Two masks run in parallel: an X for firs, seven soft dots for mushrooms.

1. Scatter is a filter, not a painter

The algorithm does not “draw an X of trees.” It does this:

  1. Pick a random point on the terrain rectangle.
  2. Convert that point to UV (0–1, 0–1).
  3. Read the mask. White ≈ 1, black ≈ 0, gray is a chance in between.
  4. Roll another random number. Keep the point only if random() ≤ keepPlacementCandidateChance.
  5. Repeat until you have count keepers, or you run out of attempts.

That last detail matters. The function tries about count * 6 candidates. A thin mask (a skinny X, or small dots) rejects most rolls. If you ask for 10,000 trees on a tiny white spec, you will get fewer than 10,000. The mask is the art direction; count is only a ceiling.

if (random() > keepPlacementCandidateChance) {
  continue // rejected
}

A fully white 1×1 texture means density is always 1, so every candidate survives. That is why the first version of the forest used a generated white mask: get placement working before you paint a map.

2. World point → UV → pixel

The terrain is a square of width TERRAIN_SIZE, centered on the origin. Local plane coordinates run from -size/2 to +size/2.

u = (x + size / 2) / size
v = (y + size / 2) / size

sampleMask then wraps those UVs and reads the red channel:

  • DataTexture (the old white 1×1) — read image.data directly.
  • A PNG loaded by useTexture — draw once into a canvas, then getImageData.

Y is flipped with (1 - v) because image rows start at the top and terrain V starts at the bottom. If your mask looks mirrored, this line is the first suspect.

Soft gray edges on the mushroom map are intentional. Near the rim of a dot, density is 0.3–0.6, so the cluster feathers out instead of cutting like a cookie stamp.

3. Seeds: random every load, repeatable when you need it

Math.random() is fine for a one-off roll. A scatter pass needs a stream of numbers: positions, keep/reject, yaw, scale. This project uses a tiny Lehmer generator:

state = (state * 16807) % 2147483647

Same seed → same forest. New seed → a different forest that still respects the mask.

In Terrain.jsx the seed is created once with useState(() => ...). That is the React-safe way to pick a random value on mount without calling Math.random() on every render. Reload the page to reshuffle. While debugging a mask, temporarily hard-code seed: 17 so the trees stop moving while you stare at them.

4. Sit on the hills, not the flat plane

The ground is a plane displaced in local Z by FBM, then the mesh is rotated [-Math.PI / 2, 0, 0]. After that rotation:

local (x, y, elevation)
    → world (x, elevation, -y)

So a placement stores plane x, y plus getTerrainElevation(x, y) — the same function that built the geometry. The instance then does:

dummy.position.set(placement.x, placement.elevation, -placement.y)
dummy.rotation.set(0, placement.rotationY, 0)

Yaw is around world Y because the trees are siblings of the rotated terrain mesh, not children of it. If you parent them under the same -90° group, yaw must rotate around local Z instead, or the trunks will lie down.

5. Instance the GLB; do not mount 80 scenes

Eighty firs as <primitive object={clone(scene)} /> means eighty scene graphs and a pile of draw calls. The fir has two meshes; the mushroom has three. The pattern is:

  1. useGLTF once.
  2. Traverse and collect { geometry, material, matrixWorld } per mesh.
  3. One <instancedMesh args={[geometry, material, count]} /> per part.
  4. For each placement, build a dummy transform, then dummy.matrix × mesh.matrixWorld so Sketchfab’s internal offsets stay correct.
composed.multiplyMatrices(dummy.matrix, localMatrix)
mesh.setMatrixAt(index, composed)

The mushroom file is about 127 units tall in native space. ScatteredMushrooms.jsx multiplies the 0.8–1.2 variety scale by MUSHROOM_BASE_SCALE = 0.0035. Always measure a Sketchfab bbox before you scatter, or one “mushroom” will be a building.

6. Variety after survival

Only accepted points get style:

  • rotationY = random() * Math.PI * 2
  • scale = 0.8 + random() * 0.4

If you randomize before the mask test, rejected points waste RNG state. Functionally it still works; keeping style after survival makes the seed’s “Nth kept tree” easier to reason about.

Build steps (from this codebase)

  1. Export a height function that matches the terrain vertex displacement.
  2. Write sampleMask(texture, u, v) and prove it with a 1×1 white texture (everything lives) and a 1×1 black texture (everything dies).
  3. Write the candidate loop: random plane point → UV → keep/reject → elevation, yaw, scale.
  4. Place instances with the (x, elevation, -y) remap.
  5. Swap in a painted mask. Look from above. The white shape should be the living area.
  6. Instance the GLB parts. If the model floats or sinks, inspect bboxMin.y and the root matrixWorld.

Exercises

  1. Temporarily seed both forests with 1. Reload three times. They must not move. Then restore random seeds.
  2. Invert the keep test (random() < keepPlacementCandidateChance vs > is easy to flip). Predict whether trees fill the X or the holes, then try it.
  3. Paint a new mask with a clearing in the middle. Confirm the UV flip: if the clearing appears on the wrong side, fix 1 - v or the plane axes, not the art first.
  4. Parent the instances under the rotated terrain group. Watch them fall over. Fix the yaw axis and write one sentence about why.
  5. Count draw calls with gl.info.render.calls for 10 mushrooms vs 160. Instancing should stay almost flat.
